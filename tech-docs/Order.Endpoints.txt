1. POST /api/orders — Place Order

Access: Buyer

This is the most important order flow because it needs to check stock and decrement it.

POST /api/orders
        │
        │ Authorization: Bearer <token>
        ▼
┌──────────────────┐
│    verifyJWT     │
└────────┬─────────┘
         │
         │ req.user
         ▼
┌──────────────────┐
│     isBuyer      │
└────────┬─────────┘
         │
         │ role === "buyer"
         ▼
┌──────────────────┐
│     validate     │
│       Zod        │
└────────┬─────────┘
         │
         ▼
┌──────────────────────────┐
│       Controller         │
│                          │
│ req.user._id             │
│ req.body                 │
└────────────┬─────────────┘
             │
             ▼
┌──────────────────────────────┐
│           Service            │
│                              │
│ Find Product                 │
│ Check product exists         │
│ Check available stock        │
│ Check requested quantity     │
│ Calculate total              │
│ Decrement stock              │
│ Create Order                 │
│ status = pending             │
└──────────────┬───────────────┘
               │
               ▼
            MongoDB
          /          \
         ▼            ▼
     Product         Order
   stock - qty      created
Example

Suppose:

Product
price = 500
stock = 20

Buyer orders:

quantity = 3

Service does:

20 - 3 = 17

Then creates:

Order
quantity = 3
price = 500
total = 1500
status = pending
buyerId = currentUser._id

The important rule is:

Requested quantity <= Available stock

If the buyer requests 25 while stock is only 20:

❌ Order rejected
❌ Stock unchanged
❌ No order created

Ideally, stock decrement + order creation should happen in a MongoDB transaction so they cannot get out of sync.

Access: Buyer

This returns only orders belonging to the logged-in buyer.

         │
         ▼
┌──────────────────────────┐

The backend should use:

req.user._id

instead of allowing the buyer to provide someone else's ID.

               │

The key is authorization based on ownership.

Buyer
order.buyerId === req.user._id
Farmer
order contains product
AND
product.farmerId === req.user._id
Admin

Admin can access the order directly.

For example:

pending
   │
   ├──────────────► completed
   │
   └──────────────► cancelled

You should prevent invalid transitions such as:

completed → pending
completed → cancelled
cancelled → completed

unless your business rules explicitly allow them.
